# Uni Playlist 客户端托管与存储设计

本文定义 Uni Playlist 后续的数据所有权、无状态接口、交换文档、服务端目录、迁移和持久化改造边界。当前代码只实现服务端托管；本文中的客户端托管、目录、导入导出和存储改造均为正式路线中的 `pending` 能力，等待网易云、QQ 音乐和 B 站当前项目范围主线收口后实施。

## 当前行为

Uni Playlist 当前支持多个独立歌单，而不是只支持一个歌单。每个歌单拥有独立的：

- `uni:<id>`；
- 名称和描述；
- 项目数量、创建时间和更新时间；
- 有序项目列表和稳定项目 ID；
- 跨平台来源引用和元数据快照。

现有创建、读取、平台来源导入、项目分页、追加、删除、排序、播放和跨平台回退均由服务端完成。生产存储将全部 Uni Playlist 及其项目共同写入：

```text
<TUNEWEAVE_DATA_DIR>/uni-playlists.json
```

因此当前语义是“多个服务端歌单共用一个数据库文件”。底层可以保存多个歌单，但尚无服务端歌单目录接口，调用方需要自行保存已创建的 `uni:<id>`。

## 数据所有权模式

后续只提供两种所有权模式：

```text
server
client
```

### Server

`server` 保持现有资源语义：

- TuneWeave 持久化歌单元数据和项目；
- 客户端只需保存 `uni:<id>`；
- 创建、读取、导入、编辑和播放均通过服务端 API；
- 适合机器人、家庭服务器、多设备共享和轻量调用方。

### Client

`client` 由客户端独占歌单数据：

- TuneWeave 不持久化歌单元数据、项目或顺序；
- 客户端自行保存稳定身份、顺序和元数据快照；
- TuneWeave 只负责平台来源展开、资源解析、元数据标准化、播放和跨平台回退；
- 服务重启不需要恢复客户端歌单；
- 同一份版本化文档可以交给其他兼容 TuneWeave 实例。

客户端模式的日常请求只提交当前需要处理的来源、项目或播放项，不得要求每次上传完整歌单。

### 不提供自动 Both

Uni Playlist 不照搬账户凭证的 `server | client | both`。初期不提供自动 `both`，因为两端并发增加、删除、排序和离线修改会引入修订号、重复项身份、快照版本及冲突合并问题，不能按平台来源 ID 简单去重。

需要两边保存时，只允许通过版本化导出和导入显式复制。服务端创建可以在实施阶段增加 `return_document=true`，但返回值只是一份当时的副本，不代表后续同步。

## 版本化交换文档

TuneWeave 只规定交换格式，不规定客户端内部存储技术。客户端可以使用 SQLite、IndexedDB、平台原生数据库、本地文件数据库或其他能够保持顺序与稳定项目 ID 的方案。JSON 只用于导出、导入、备份、迁移和跨客户端交换。

首版公共格式标识规划为：

```text
tuneweave_uni_playlist_v1
```

文档至少包含：

- 格式版本；
- 歌单稳定 ID、名称和描述；
- 创建时间和更新时间；
- 有序项目列表；
- 每个项目的稳定 ID、类型和添加时间；
- 平台来源引用；
- 元数据快照；
- 安全且有明确用途的扩展字段。

文档不得包含：

- 账户 Cookie、token 或调用方凭证；
- 密码、验证码或 QQ 设备身份；
- 临时媒体地址、平台签名或任意请求头。

客户端提交的快照只用于展示和严格匹配，不能代替 provider 的真实资源校验、播放授权、会员状态或音质判断。

## 无状态客户端接口

下列路径是实施候选，最终可按现有 API 命名规范调整；能力与安全边界不能被弱化。

### 展开平台集合

```text
POST /v1/uni/materialize/imports
```

接受一个或多个平台歌单、收藏夹、合集或其他可播放集合，完整分页读取来源，按“来源顺序 → 来源内部顺序”返回标准化文档或项目序列，并保留重复项。该请求不得创建 `uni:<id>` 或写入服务端持久化存储。

大型结果必须采用受控分页、流式响应或压缩传输，不能依赖无限大的单次 JSON 响应。

### 标准化资源

```text
POST /v1/uni/materialize/items
```

接受歌曲、MV、视频、播客节目、广播等一个或一批平台引用，由对应 provider 获取真实元数据并返回标准化 `UniPlaylistItem`。请求必须限制批量数量、响应体大小、超时和上游分页范围。

### 播放客户端托管项目

```text
POST /v1/uni/items/stream
```

客户端只提交当前播放的一个 `UniPlaylistItem`，可以同时选择播放平台、回退顺序、音质、清晰度和账户。TuneWeave 使用来源引用和快照执行原平台播放或严格跨平台匹配，不要求知道该项目属于哪个客户端歌单，也不保存提交内容。

需要 GET 或 302 流程时，可以增加：

```text
POST /v1/uni/items/playback-tickets
GET  /v1/playback/{ticket}/redirect
```

播放票据必须只存在于内存、短期有效、单次或有限次数使用，且不能包含可由调用方篡改的任意目标 URL。服务重启后票据可以失效；它不属于用户业务数据。

## Server 多歌单管理

现有 Server 模式补充以下能力：

```text
GET    /v1/uni/playlists
PATCH  /v1/uni/playlists/{ref}
DELETE /v1/uni/playlists/{ref}
```

目录分页返回服务端保存的 `uni:<id>`、名称、描述、项目数及创建/更新时间，使用稳定排序且不内联全部项目。修改只管理名称和描述；删除必须明确指定目标并原子移除该歌单及项目，不能因为外部平台来源失效而自动删除本地歌单。

目录和元数据接口不得泄露账户凭证或其他私有服务端状态。

## Server 与 Client 显式迁移

规划接口：

```text
GET  /v1/uni/playlists/{ref}/export
POST /v1/uni/playlists/import-document
```

服务端导出生成完整版本化文档，保留顺序、重复项、稳定项目 ID 和快照，不包含凭证或临时播放信息。大型歌单必须支持流式、压缩或其他受控下载方式。

文档导入在完整验证后原子创建服务端歌单：

- 任一项目不合法时不得产生部分记录；
- 默认生成新的服务端 `uni:<id>`；
- 只有明确且安全时才允许保留原 ID；
- ID 冲突不得静默覆盖；
- 导入不建立后续自动同步关系。

Server 模式的 `uni:<id>` 表示服务端资源；Client 模式的歌单和项目 ID 只在客户端文档内稳定。无状态接口不得接受一个服务端不存在的 `uni:<id>` 后隐式寻找客户端数据。

## 服务端持久化改造

现有单文件后端在追加、删除或排序时可能克隆并重写全部歌单，随着多个大型歌单和 B 站视频集合增加，会产生写放大、锁持有时间、内存峰值、整体解析成本和扩大损坏影响范围的问题。

实施阶段在以下方案中选择一种，不引入必须独立部署的外部数据库服务。

### 按歌单拆分文件

```text
<TUNEWEAVE_DATA_DIR>/uni-playlists/
├── index.json
├── pl_xxx.json
├── pl_yyy.json
└── pl_zzz.json
```

要求：

- 修改一个歌单只重写该歌单文件；
- 索引只保存目录所需元数据；
- 单歌单损坏不能静默影响其他歌单；
- 保留原子发布和 Windows 中断恢复；
- 提供旧 `uni-playlists.json` 的一次性安全迁移。

### 嵌入式数据库

至少建立 playlists、playlist_items、稳定项目 ID、位置索引和版本字段，提供原子事务与数据格式迁移。具体 Rust 库在实施时根据依赖体积、可移植性、事务能力和维护成本决定。

无论选择哪种方案，迁移失败都不得覆盖旧数据；成功切换前必须能够从原文件恢复。

## 凭证与安全

客户端歌单不能绑定服务端账户别名。账户选择继续通过：

- `X-TuneWeave-Credential`；
- `account`；
- `accounts`。

实施时至少限制：

- 单歌单项目数和单请求批量数；
- 文档解码体积、JSON 深度和字符串长度；
- 单项目快照和扩展字段大小；
- 导入来源数、上游分页总量和响应体大小；
- 流式响应的超时、中断和取消；
- 危险 URL、未知平台和畸形引用。

任何无状态调用都不能允许调用方覆盖 provider 的通用代理、固定域名、请求头或重定向策略。

## 验收标准

### Server

- 可以创建和分页枚举多个 Uni Playlist；
- 每个歌单可以独立读取、修改、删除和排序；
- 大型歌单修改不再重写全局数据库；
- 重启后目录、项目和顺序完整恢复；
- 旧单文件数据安全迁移，失败不覆盖原数据。

### Client

- 来源展开、单项标准化和单项播放均不写入 Uni Playlist 持久化存储；
- 播放与跨平台回退不要求上传完整歌单；
- 同一客户端文档可由另一兼容实例处理；
- 服务重启后没有需要恢复的客户端歌单状态；
- 客户端模式测试目录不产生 Uni Playlist 数据文件。

### 迁移

- Server 导出文档可由 Client 保存和播放；
- Client 文档可原子导入 Server；
- 顺序、重复项、稳定项目 ID 和快照不丢失；
- Cookie、token、调用方凭证和临时媒体地址不会进入文档；
- 复制不会被表述或实现为自动同步。

## 路线与发布边界

本阶段位于前三个平台项目范围收口之后、酷狗/咪咕/酷我公开音源补充层之前，属于首个 pre-release 的功能范围。原因是测试版之后再改变所有权语义、公共交换格式和服务端持久化结构会产生较高兼容成本。

B 站延期登录、后三个平台完整账户能力、验证码服务本地 Rust 实现和平台功能扩展仍不阻塞首个 pre-release。
