# Uni Playlist 客户端托管与存储设计

本文定义 Uni Playlist 的数据所有权、无状态接口、交换文档、服务端目录和持久化边界。服务端目录、客户端 V1 文档、无状态处理链及按歌单拆分存储均已完成。

## 当前行为

Uni Playlist 当前支持多个独立歌单，而不是只支持一个歌单。每个歌单拥有独立的：

- `uni:<id>`；
- 名称和描述；
- 项目数量、创建时间和更新时间；
- 有序项目列表和稳定项目 ID；
- 跨平台来源引用和元数据快照。

现有创建、读取、平台来源导入、项目分页、追加、删除、排序、播放和跨平台回退均由服务端完成。生产存储按歌单写入：

```text
<TUNEWEAVE_DATA_DIR>/uni-playlists/<playlist-id>.json
```

目录索引在启动时从记录重建并保存在内存，单歌单修改只发布对应记录。服务端可以通过 `GET /v1/uni/playlists` 分页列出歌单，以 `PATCH /v1/uni/playlists/{ref}` 修改名称或描述，并以 `DELETE` 原子删除整份歌单。

## 数据所有权模式

后续只提供两种所有权模式：

```text
server
client
```

### Server

`server` 保持现有资源语义：

- TuneWeave 持久化歌单元数据和项目；
- 客户端只需保存 `uni:<id>`；
- 创建、读取、导入、编辑和播放均通过服务端 API；
- 适合机器人、家庭服务器、多设备共享和轻量调用方。

### Client

`client` 由客户端独占歌单数据：

- TuneWeave 不持久化歌单元数据、项目或顺序；
- 客户端自行保存稳定身份、顺序和元数据快照；
- TuneWeave 只负责平台来源展开、资源解析、元数据标准化、播放和跨平台回退；
- 服务重启不需要恢复客户端歌单；
- 同一份版本化文档可以交给其他兼容 TuneWeave 实例。

客户端模式的日常请求只提交当前需要处理的来源、项目或播放项，不得要求每次上传完整歌单。

### 不提供自动 Both

Uni Playlist 不照搬账户凭证的 `server | client | both`。初期不提供自动 `both`，因为两端并发增加、删除、排序和离线修改会引入修订号、重复项身份、快照版本及冲突合并问题，不能按平台来源 ID 简单去重。

需要两边保存时，只允许通过版本化导出和导入显式复制。服务端创建可以在实施阶段增加 `return_document=true`，但返回值只是一份当时的副本，不代表后续同步。

## 版本化交换文档

TuneWeave 只规定交换格式，不规定客户端内部存储技术。客户端可以使用 SQLite、IndexedDB、平台原生数据库、本地文件数据库或其他能够保持顺序与稳定项目 ID 的方案。JSON 只用于导出、导入、备份、迁移和跨客户端交换。

首版公共格式标识规划为：

```text
tuneweave_uni_playlist_v1
```

该标识现已由 `UniPlaylistDocumentFormat::V1` 固定表达，未知格式不会退化为 V1。文档 JSON 使用拒绝未知字段的强类型结构，而不是允许任意 JSON 穿透的容器；文档级扩展目前只声明 `duplicates_preserved=true`，项目级扩展只允许完整的导入来源索引、来源引用、来源类型和可选原项目 ID，快照扩展只允许播放匹配与展示所需的规范引用、可播放性、音质档位、视频/播客/电台静态摘要。扩展协议新增字段必须通过后续格式版本或明确兼容修订进入，不能把凭据或传输状态塞进任意键。

文档至少包含：

- 格式版本；
- 歌单稳定 ID、名称和描述；
- 创建时间和更新时间；
- 有序项目列表；
- 每个项目的稳定 ID、类型和添加时间；
- 平台来源引用；
- 元数据快照；
- 安全且有明确用途的扩展字段。

文档不得包含：

- 账户 Cookie、token 或调用方凭证；
- 密码、验证码或 QQ 设备身份；
- 临时媒体地址、平台签名或任意请求头。

客户端提交的快照只用于展示和严格匹配，不能代替 provider 的真实资源校验、播放授权、会员状态或音质判断。

V1 校验要求名称、描述及文本快照已经规范化，项目 ID 唯一、位置从零连续、`item_count` 与实际数组一致，来源必须是外部平台引用，项目时间不得晚于文档更新时间，并保留同一来源的多次出现。单份文档最多 100,000 项；这一结构上限不替代 HTTP 导入时更严格的请求体、超时和内存限制。封面是唯一允许的 URL 字段，只接受受限 HTTPS 展示地址；服务端不得根据文档封面发起资源或媒体请求。

## 无状态客户端接口

下列路径是实施候选，最终可按现有 API 命名规范调整；能力与安全边界不能被弱化。

### 展开平台集合

```text
POST /v1/uni/materialize/imports
```

该接口已实现。它接受一个或多个平台歌单、收藏夹、合集或其他可播放集合，与 Server 导入共用完整分页和账户隔离逻辑，按“来源顺序 → 来源内部顺序”返回带全局位置和确定性 ID 的标准化客户端项目页，并保留重复项。该请求不会创建 `uni:<id>` 或写入服务端持久化存储。

响应使用 `limit=1..500/offset=0..100000` 的受控分页，集合总量最多 100,000 项，单来源最多 2,000 个上游页；来源游标不推进或越界时直接失败，不能依赖无限大的单次 JSON 响应。返回的来源摘要会清除服务器账户别名。

### 标准化资源

```text
POST /v1/uni/materialize/items
```

该接口已实现：一次接受 1–100 个歌曲、MV、视频、播客节目或广播引用，由对应 provider 获取真实元数据并返回 V1 安全 `UniPlaylistDocumentItem`。项目按输入顺序从零编号，重复来源各自获得稳定项目 ID；分平台账户只用于本次解析，不进入客户端数据。成功及各类输入失败均已验证不会创建 Uni Playlist 数据文件。批量上限与统一上游超时共同限制资源使用，本接口不执行上游集合分页。

### 播放客户端托管项目

```text
POST /v1/uni/items/stream
```

该接口已实现。客户端只提交当前播放的一个 V1 `UniPlaylistDocumentItem`，可以同时选择播放平台、回退顺序、音质、清晰度和账户。TuneWeave 完整验证项目安全边界后，与 Server 模式共用原平台播放和严格跨平台匹配链；不要求知道该项目属于哪个客户端歌单，不读取或写入 Uni Playlist 存储，响应也不会虚构歌单引用。

需要 GET 或 302 流程时，可以增加：

```text
POST /v1/uni/items/playback-tickets
GET  /v1/playback/{ticket}/redirect
```

播放票据必须只存在于内存、短期有效、单次或有限次数使用，且不能包含可由调用方篡改的任意目标 URL。服务重启后票据可以失效；它不属于用户业务数据。

## Server 多歌单管理

现有 Server 模式补充以下能力：

```text
GET    /v1/uni/playlists
PATCH  /v1/uni/playlists/{ref}
DELETE /v1/uni/playlists/{ref}
```

目录分页返回服务端保存的 `uni:<id>`、名称、描述、项目数及创建/更新时间，按 `created_at_ms` 降序、同时间 ID 升序稳定排序且不内联全部项目。修改只管理明确提交的名称和描述，并以相同值不改时间、不重写文件的幂等语义发布；删除必须明确指定目标并在一次发布中移除该歌单及项目，不能因为外部平台来源失效而自动删除本地歌单。删除结果只报告移除数，不把完整项目数组复制到响应。

目录和元数据接口不得泄露账户凭证或其他私有服务端状态。

## Server 与 Client 显式复制

规划接口：

```text
GET  /v1/uni/playlists/{ref}/export
POST /v1/uni/playlists/import-document
```

服务端导出已通过 `GET /v1/uni/playlists/{ref}/export` 生成完整版本化文档：元数据与项目在同一存储读快照中取得，保留顺序、重复项、稳定项目 ID 和安全快照，未知存储扩展不会穿透，响应禁止中间缓存且不包含凭证或临时播放信息。当前 V1 结构上限为 100,000 项；调用方可通过标准 `Accept-Encoding: gzip` 请求压缩响应，序列化和压缩均在阻塞任务中完成，压缩链不会额外保留完整 identity 响应缓冲。`gzip;q=0` 明确保持未压缩响应，两种传输解码后的安全文档一致。

文档导入现已通过 `POST /v1/uni/playlists/import-document` 在 16 MiB 请求上限内完整验证后原子创建服务端歌单：

- 任一项目不合法时不得产生部分记录；
- 默认生成与文档 ID 不同的新服务端 `uni:<id>`，同时保留项目稳定 ID；
- 只有显式 `preserve_id=true` 时才允许尝试保留原歌单 ID；
- ID 冲突不得静默覆盖；
- 导入不建立后续自动同步关系，响应明确返回 `automatic_sync=false`。

Server 模式的 `uni:<id>` 表示服务端资源；Client 模式的歌单和项目 ID 只在客户端文档内稳定。无状态接口不得接受一个服务端不存在的 `uni:<id>` 后隐式寻找客户端数据。

## 服务端持久化改造

现有单文件后端在追加、删除或排序时可能克隆并重写全部歌单，随着多个大型歌单和 B 站视频集合增加，会产生写放大、锁持有时间、内存峰值、整体解析成本和扩大损坏影响范围的问题。

综合依赖体积、跨平台发布、单歌单事务边界和维护成本，已经选择按歌单拆分文件，不引入嵌入式或外部数据库依赖。

### 按歌单拆分文件

```text
<TUNEWEAVE_DATA_DIR>/uni-playlists/
├── store.json
├── pl_xxx.json
├── pl_yyy.json
└── pl_zzz.json
```

要求：

- 修改一个歌单只重写该歌单文件；
- 启动时从每份记录重建内存目录索引，不维护需要跨文件事务的 `index.json`；
- `store.json` 只保存目录格式版本，不保存歌单目录元数据；
- 单歌单损坏不能静默影响其他歌单；
- 保留原子发布和 Windows 中断恢复。

该后端已经投入生产入口：记录带独立格式版本，创建、元数据修改、项目追加/删除/重排均只克隆和发布目标歌单；未发布临时文件在启动时清理，Windows 单文件替换备份沿用可恢复发布语义。严格加载会拒绝未知记录版本、文件名与歌单 ID 不一致、损坏项目序列和意外目录内容，不会自动覆盖。

### 未采用：嵌入式数据库

嵌入式数据库仍可作为未来规模显著增长后的替代方向，但当前不会为 Uni Playlist 引入额外运行库、数据库文件锁和 schema 管理框架。首个正式 Release 前只验收全新部署的当前目录格式，不读取或转换开发期旧存储。

## 凭证与安全

客户端歌单不能绑定服务端账户别名。账户选择继续通过：

- `X-TuneWeave-Credential`；
- `account`；
- `accounts`。

实施时至少限制：

- 单歌单项目数和单请求批量数；
- 文档解码体积、JSON 深度和字符串长度；
- 单项目快照和扩展字段大小；
- 导入来源数、上游分页总量和响应体大小；
- 流式响应的超时、中断和取消；
- 危险 URL、未知平台和畸形引用。

任何无状态调用都不能允许调用方覆盖 provider 的通用代理、固定域名、请求头或重定向策略。

## 验收标准

### Server

- 可以创建和分页枚举多个 Uni Playlist；
- 每个歌单可以独立读取、修改、删除和排序；
- 大型歌单修改不再重写全局数据库；
- 重启后目录、项目和顺序完整恢复。

### Client

- 来源展开、单项标准化和单项播放均不写入 Uni Playlist 持久化存储；
- 播放与跨平台回退不要求上传完整歌单；
- 同一客户端文档可由另一兼容实例处理；
- 服务重启后没有需要恢复的客户端歌单状态；
- 客户端模式测试目录不产生 Uni Playlist 数据文件。

### 显式复制

- Server 导出文档可由 Client 保存和播放；
- Client 文档可原子导入 Server；
- 顺序、重复项、稳定项目 ID 和快照不丢失；
- Cookie、token、调用方凭证和临时媒体地址不会进入文档；
- 复制不会被表述或实现为自动同步。

## 路线与发布边界

本阶段位于前三个平台项目范围收口之后、酷狗/咪咕/酷我/汽水音乐公开音源补充层之前，属于首个 pre-release 的功能范围。原因是测试版之后再改变所有权语义、公共交换格式和服务端持久化结构会产生较高兼容成本。

B 站延期登录、后四个平台完整账户能力、验证码服务本地 Rust 实现和平台功能扩展仍不阻塞首个 pre-release。
