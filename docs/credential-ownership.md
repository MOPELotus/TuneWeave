# 调用方托管凭证契约

状态：QQ 与网易云当前已实现的公开业务端点已经完成接入。版本化封装、请求头校验、多平台隔离、登录导出、刷新、退出、公开与账户目录、账户读写、Uni Playlist 导入、播放回退以及两平台安全原始扩展均遵循本契约。二维码、密码和验证码登录支持 `server/client/both`，两平台均在强类型凭证导入和实际登录导出完成后声明 `caller_managed_credentials`。匿名身份、anti-cheat token 和尚未完成的登录挑战不是账户资源，不从调用方业务凭证中读取状态；后续 provider 必须从首个账户功能起同时实现两种凭证所有权模式。

## 目标与兼容边界

TuneWeave 必须同时服务两类调用方：

- 由 API 服务器管理登录态的应用继续使用 `platform + account`，凭证保存在服务器私有数据目录，现有调用方式和缺省行为不变。
- 自己管理账户数据的应用可以让登录结果只返回给调用方而不写入服务器，并在后续请求中按次携带该凭证。

调用方托管不是原始 Cookie、token、代理或任意请求头注入接口。TuneWeave 只接受自己定义且通过对应 provider 强类型校验的版本化凭证封装；平台域名、请求签名、设备字段和传输请求头仍由 provider 控制。

## 登录凭证模式

所有会产生登录态的入口统一增加 `credential_mode`：

| 值 | 服务器持久化 | 返回调用方 | `account` 语义 |
| --- | ---: | ---: | --- |
| `server` | 是 | 否 | 缺省模式；省略时使用 `default`，与现有行为兼容 |
| `client` | 否 | 是 | 不创建服务器账户别名；请求不得同时提交非空 `account` |
| `both` | 是 | 是 | 按指定别名持久化，同时返回同一凭证；省略别名时使用 `default` |

二维码创建、验证码挑战创建等多步登录必须在首个请求中固定模式，并把模式保存在只存在于内存且有期限的事务里；轮询或验证阶段不能临时切换。密码等单步登录直接在同一响应应用该模式。平台确认成功但持久化失败时，`server/both` 不能伪报完整成功；`client` 不得因为服务器未配置账户存储而失败或写盘。

只有显式选择 `client` 或 `both` 的成功登录/刷新响应可以出现 `caller_credential`：

```json
{
  "format": "tuneweave_credential_v1",
  "platform": "qq",
  "value": "twc1_<opaque-base64url>",
  "expires_at": null
}
```

`value` 是调用方应保存和回传的完整 bearer secret；其内部格式不构成公共字段契约。`opaque` 只表示调用方不应解析，不承诺静态加密。它不得依赖某一台 TuneWeave 服务器的临时内存或实例密钥，使调用方保存的 v1 凭证可以交给其他兼容实例使用；解析端仍必须校验版本、平台、provider 凭证种类、字段边界和完整结构。

包含 `caller_credential` 的响应必须设置 `Cache-Control: no-store` 与 `Pragma: no-cache`。二维码确认结果只在完成响应中交付一次，事务随后销毁；调用方若在收到响应前断线，应重新登录，而不是通过普通状态端点找回敏感值。

## 业务请求携带方式

调用方凭证只通过可重复的请求头传入：

```http
X-TuneWeave-Credential: twc1_<opaque-base64url>
```

禁止把它放入 URL、查询参数、资源引用、Uni Playlist 数据或普通 JSON 业务体。单个请求最多接受 8 份凭证，每份解码后最多 64 KiB；每个平台最多一份，重复、畸形、未知版本或平台不匹配均在访问上游前返回 `invalid_request`。

普通请求按目标平台独立解析凭证来源：

1. 该平台存在调用方凭证时使用它，并且不再隐式读取该平台的 `default` 账户。
2. 没有调用方凭证时，继续按显式 `account`、跨平台 `accounts` 映射或现有默认策略读取服务器账户。
3. 同一平台同时出现调用方凭证和显式服务器账户别名时返回 400，不以任意优先级静默覆盖。
4. 多平台搜索、Uni Playlist 导入、播放回退和解析器可以为不同平台分别使用重复请求头中的调用方凭证，或与其他平台的服务器账户组合；任何凭证都不能跨平台借用。

公开且不需要认证的请求可以在校验后不注入凭证。需要设备身份、签名或 Cookie 的请求仍由 provider 从选中的强类型凭证生成固定协议字段，调用方不能覆盖目标 URL、代理、来源 IP、User-Agent 或附加请求头。

## 状态、刷新与退出

- `GET /v1/auth/session` 接受服务器 `platform + account` 或一份调用方凭证，返回相同的脱敏状态模型，永不回显凭证。
- `POST /v1/auth/session/refresh` 使用服务器账户时原子替换该别名；使用调用方凭证时不落盘并返回新的 `caller_credential`。`credential_mode=both` 必须同时给出同一身份的调用方凭证与账户别名，成功后原子保存并返回同一新代际，失败不得覆盖旧代际。
- `DELETE /v1/auth/session` 使用服务器账户时删除精确别名；使用调用方凭证时只执行平台退出并返回 `caller_credential_discard_required=true`，不能声称删除了调用方自己的存储。`both` 模式还需删除匹配的服务器别名。
- 刷新或退出同时提供两种来源时，服务器必须先验证平台身份一致；不一致时在发网和写盘前拒绝。

## 安全与验收要求

- 专用请求头、解码后的封装和 provider 原始凭证必须进入全链路脱敏表；访问日志、追踪、Debug、错误详情、panic、指标标签、扩展字段和重定向响应均不得包含它们。
- 生产环境必须使用 HTTPS。反向代理不得记录该请求头；浏览器部署只允许明确配置的来源和请求头，不以通配 CORS 暴露 bearer secret。
- `client` 登录须用独立临时数据目录验证成功后没有账户文件或凭证代际产生；服务重启后也不得恢复该登录态。
- `server` 回归测试必须证明现有账户持久化、刷新、退出和默认别名行为不变；`both` 必须证明落盘值与返回值代表同一凭证代际。
- 每个 provider 分别测试封装导出、导入、过期、平台错配、未知版本、超限、畸形结构和上游认证错误；不以通用裸 JSON 代替已知平台凭证模型。
- 跨平台测试至少覆盖两个调用方凭证并存、调用方凭证与另一平台服务器账户混用、同平台冲突拒绝，以及播放回退不会把原平台凭证发给候选平台。

每个平台只有在强类型凭证导入和该平台实际登录导出均完成后才声明 `caller_managed_credentials`；刷新、退出和新增账户端点继续逐项同步 README、API 端点表、平台账本与真实登录验收记录。QQ 与网易云的登录、刷新和退出代码链已经完成离线协议验收；其中 QQ 刷新、网易云调用方刷新/退出仍保留真实账户成功态联合验收，不以离线覆盖冒充在线验证。
